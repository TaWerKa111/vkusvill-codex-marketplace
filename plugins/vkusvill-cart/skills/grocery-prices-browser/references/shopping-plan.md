# Список из чата и план покупок — контракт v1

Подготовлено для **0.9.0, не опубликовано**. Сначала проверить фактически доступные инструменты. На работающей 0.8.0 сохраняются `prices_search`, `products_search`, `prices_browser_show` и прежние действия ВкусВилла; новые команды и `correlation` нельзя отправлять, пока их нет в схеме подключённого сервера. Файл описывает согласованный контракт; локальный валидатор проверяет согласованность примеров, а не работу живого MCP/хоста.

Пользователь пишет список в существующем чате. Агент открывает панель, читает `shoppingWorkspace` из контекста и создаёт/изменяет потребности с исходными количеством и единицей. Выбор сетей — явный охват исследования, отдельно от выбора предложения в покупку. Не создавать новый чат и не менять корзины сайтов автоматически.

## Общие поля и подтверждение

Все три команды требуют `operation_id` (новый UUID), `workspace_id` (UUID из панели) и `expected_revision` (целое число >= 0 из текущего контекста). Не угадывать идентификаторы или ревизию: открыть панель, если контекста нет. Неизвестные поля запрещены. Синтетические аргументы каждого инструмента находятся в [shopping-plan-examples.json](shopping-plan-examples.json); весь массив не отправлять одним вызовом. Это учебные данные с условными ревизиями и фиксированным временем, не наблюдения магазина и не исполняемый сценарий для личной панели.

Ответ сервера имеет `status: "prepared"` и `shoppingCommand` с `version: 1`, типом из таблицы и проверенными аргументами.

| Инструмент | shoppingCommand.type |
| --- | --- |
| `shopping_plan_update` | `plan_update` |
| `shopping_research_update` | `research_update` |
| `shopping_offer_select` | `offer_select` |

Это подготовка команды. Применение подтверждает панель через `lastShoppingOperation` с тем же `operation_id`, статусом и `persisted`. Контекст содержит `shoppingWorkspace.id`, `revision`, `context_revision`, `store_ids`, строки с `item_revision`, исследование и ссылки на кандидатов с причинами недоступности.

| Статус панели | Действие агента |
| --- | --- |
| `applied`, `persisted: true` | Можно сказать, что изменение сохранено. |
| `already_applied`, `persisted: true` | Идентичная команда уже сохранена; не повторять как новую. |
| `applied_session_only`, `persisted: false` | Честно сообщить: только текущая сессия, сохранение после перезагрузки не подтверждено. |
| `conflict` | Прочитать новый контекст, пересмотреть намерение и отправить новую команду с новым UUID. |
| `failed` | Сообщить причину и доступное действие; не заявлять успех. |

При потерянном ответе сначала читать подтверждение панели. Повторять тот же UUID можно только с идентичным содержимым; повторный UUID с изменённой командой конфликтует. Старая команда не должна восстанавливать удалённую строку. Сервер не сохраняет личный план; подтверждение относится к локальному состоянию панели. Отсутствие рабочего хоста, хранилища или блокировок нельзя скрывать за словом «сохранено».

## shopping_plan_update

`changes` — массив 0–100 действий с уникальными `item_id`; допускается пустой при наличии `store_ids`. Хотя бы одно изменение или поле `store_ids` обязательно. `store_ids`, если задан, полностью заменяет охват, включая `[]`; максимум 17 уникальных ID из [реестра](stores.json).

- `upsert`: `action`, `item_id`, `name`, `quantity`, `unit`. ID соответствует `[A-Za-z0-9-]{1,80}`, название после удаления внешних пробелов — 1–200 единиц UTF-16 (например, символ 🥛 занимает две), количество конечное .01–1000, единица `шт|кг|л`. Это полное требуемое количество, не прибавка. Цены и предложения здесь запрещены.
- `remove`: только `action`, `item_id`; удаление отсутствующей строки безопасно.

`changes` можно не передавать при редактировании только охвата: по умолчанию это `[]`. Ревизии — безопасные целые числа до 9007199254740991. Итоговый список ограничен 100 строками. Одинаковые названия с разными ID не объединяются. Неизменённая потребность сохраняет заметки и предложения; изменение названия/количества/единицы меняет `item_revision`, делает старое исследование неактуальным и перепроверяет зависимые выборы. Ошибочное действие отклоняет всю команду.

## shopping_research_update

Поля сверх общих: `action: start|resume|checking`, UUID `research_id`, UUID `attempt_id`, непустые уникальные `item_ids` (до 100) и `store_ids` (до 17). Строки должны существовать, сети должны входить в выбранный охват.

`start` фиксирует потребности, их ревизии и текущие город/район/способ получения с `context_revision`; создаёт задачи «ожидает». Команда сама не просматривает сайты. `checking` помечает только текущие ожидающие задачи. `resume` оставляет успешные результаты, берёт только незавершённые/заблокированные/ошибочные задачи в указанном подмножестве и требует новый `attempt_id` при прежнем контексте и потребности. Если они изменились, нужен новый явный `start`.

При входе/CAPTCHA продолжить остальные сети. Кнопка продолжения передаёт узкий запрос в тот же чат: нужная сеть и незавершённые позиции. Агент возобновляет после действия пользователя, не решает CAPTCHA и не собирает cookies. Неясный результат отправки сообщения требует проверки состояния, а не автоматического повтора.

## prices_browser_show: необязательная correlation

Для привязки наблюдения к исследованию добавить строгий объект `correlation` с UUID `workspace_id`, `research_id`, `attempt_id`, строкой `item_id`, целыми `item_revision >= 1` и `context_revision >= 0`. Остальной [формат наблюдений](observations.md) прежний: один точный запрос `q` в пределах 1–200 единиц UTF-16 после удаления внешних пробелов, город, непустые продукты или проверки, только импортируемые сети. Запрос `q` совпадает с именем потребности, без сокращения и смены регистра; его границы расширены только у `prices_browser_show` в подготовленной 0.9.0. Каталожный `prices_search` сохраняет 2–120. Сервер проверяет форму; актуальность исследования подтверждает панель.

Панель принимает связь только при совпадении рабочего пространства, исследования, попытки, строки/ревизии, контекста, запроса и выбранных сетей. Опоздавший результат после изменения города, потребности, удаления или продолжения не завершает текущую задачу. Связанный импорт не создаёт потребность «1 шт» и не меняет заказанное количество. Старый импорт без связи остаётся доступным в сравнении, но не завершает задачу только по совпадению названия.

Товары дают результаты и количество допустимых кандидатов; `not_found` означает завершённую проверку без совпадений; `login_required|captcha|address_required` требуют действия; `error|browser_unavailable` означают сбой. Справочный каталог остаётся ограниченным результатом. Текущий прогресс выводится из принятого актуального наблюдения, с учётом временных меток и отрицательных перепроверок.

## shopping_offer_select

Поля сверх общих: `item_id`, `item_revision >= 1`, `store` и `observation: {id, scope, fulfillment, checkedAt, url}`. `id` — 1–120 символов, `scope` — 1–200, URL — официальный HTTPS до 1000 символов, `fulfillment` — `delivery|pickup|in_store|unknown`, время UTC ISO. Выбирать ссылку из текущего контекста панели, не составлять цену самостоятельно. Все пять полей ссылки обязательны; цена, фасовка, название и заявленная пригодность здесь запрещены.

Ссылка должна однозначно найти уже импортированный кандидат. Панель заново проверяет потребность, точную локацию, актуальность, остаток, упаковку, обычную цену, соответствие и историю отрицательных проверок. Условные цены остаются справочными даже при `conditionsConfirmed=true`. Неизвестная фасовка не превращается в одну штуку. Для потребности 2 л и упаковки 0,9 л нужны 3 упаковки; цена за литр не является итогом покупки.

Результат — выбор в местный список соответствующего магазина. Одновременные назначения в несколько сетей считаются явно, без обещания экономии. Команда не добавляет товары в корзину ВкусВилла. Реальная ссылка и проверяемый перенос доступны только у ВкусВилла через прежний отдельный сценарий: перепроверка каталога, неизменный предпросмотр на пять минут, подтверждение и защита от повторного переноса. Оформление и оплата происходят у магазина.
